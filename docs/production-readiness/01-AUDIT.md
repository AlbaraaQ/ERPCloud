# 01 — Audit

كل بندٍ هنا مُتحقَّق منه بالتشغيل، لا بالتخمين. البيئة التي أُجري فيها الفحص:
PostgreSQL 16 مضمّن، 112 ترحيلًا مطبَّقًا، بذرة `demo`، الـ API على `:3000`، تسجيل
دخول ناجح بـ `owner@demo.test`. كل رقم أدناه مُلتقط من استجابة حقيقية.

## أ. الستايل والتصميم العام (البندان 1 و2)

**الحالة:** مفتوح. PR-1 بنى الأساس (نظام الرموز، الوضع الداكن، 22 مكوّنًا مشتركًا)
لكنه **لم يُعِد تصميم الشاشات نفسها**. الشريط الجانبي في `apps/staff/components/app-shell.tsx`
ما زال يستخدم أصناف CSS القديمة (`nav-legend`, `dot ready`) بدل مكوّنات `packages/ui`،
فلا يستفيد من نظام التصميم v3.

**ما يحتاجه:** جولة تصميم حقيقية على القشرة (الشريط الجانبي + الشريط العلوي +
المحتوى) تُبدل الأصناف القديمة بمكوّنات `@erp/ui`، مع الحفاظ على عرض 288px وارتفاع
شريط 56px ومقياس محتوى 1400px كما ينصّ العقد.

## ج. نقاط البيع (البندان 4 و5 و6)

### ج-1 — سبب فشل الحفظ: الراية مطفأة

```
GET /api/v1/pos/settings → 404
{"code":"NOT_FOUND","detail":"POS pack is disabled for this tenant"}
```

المصدر: `apps/api/src/modules/pos/pos.service.ts:171`. والسبب في بيانات المستأجر:

```
GET /api/v1/settings → "feature.pos": false
                       "feature.projects": false
                       "feature.hrm": false
                       "feature.niche": false
```

**وهذا هو السبب الجذري لمعظم الشاشات "التي لا تفتح"**: المستأجر `demo` بلا اشتراك
نشط (`GET /billing/subscription` → `data: null`)، فكل راية وحدةٍ فيه `false`، وكل
شاشةٍ محميّةٌ براية تُعيد 404. ليست الشاشة مفقودة — المستأجر لا يملكها.

**ملاحظة مهمة:** `packages/database/src/seed-demo.ts:219` يُبذر `feature.pos: true`
للباقة الاحترافية، لكن ذلك **حقوق خطة** لا إعداد مستأجر؛ ولا شيء يطبّق حقوق الخطة على
`tenant_settings` عند تفعيل الاشتراك. هذه ثغرة في آلية التمكين، لا في البذرة.

### ج-2 — لا عميل عام ولا مورد عام

```
GET /api/v1/parties?limit=3 → 200 []      ← لا طرف واحد في الدفتر
```

المطلوب (البند 5) طرفان نظاميَّان افتراضيَّان: **عميل عام** و**مورد عام**، يُنشأان
مع كل فرع/مستأجر، ويظهران في POS كخيار افتراضي.

### ج-3 — منطق الفاتورة المبوّسة/القياسية منجزٌ سلفًا

`apps/api/src/modules/einvoicing/einvoicing.service.ts:492`:

```ts
const profile: 'standard' | 'simplified' = buyer?.vatNo ? 'standard' : 'simplified';
```

المنطق صحيح ومطابق لقاعدة هيئة الزكاة. **الناقص ليس المنطق** — الناقص هو الطرف العام
(ج-2) حتى يكون للفاتورة مشترٍ يُقاس وجود رقمه الضريبي. وشاشة POS فيها وضع "عميل نقدي"
لكنه يرسل `cashCustomerName` نصًّا حرًّا لا `partyId` يشير إلى طرف "عميل عام".

## د. الإشعارات والأوفلاين (البند 7)

```
GET /api/v1/notifications?limit=5 → 200 {"data":[],"meta":{"total":0,"unread":0}}
```

الشاشة **تفتح**، لكنها فارغة: لا إشعار واحد مبذور للمستأجر demo. إن كان المقصود "لا
تفتح" فهو على الأرجح انهيارٌ في المتصفح يحتاج فحصًا حيًّا بـ DevTools؛ وإن كان المقصود
"تفتح وفاضية" فالسبب أن البذرة لا تكتب إشعارات.

شاشات الأوفلاين (`pos/offline`, `pos/offline-queue`) تعتمد IndexedDB (`lib/offline-db.ts`)
ومحرّك مزامنة (`lib/sync-engine.ts`)، وكلاهما يحتاج فحصًا في متصفح حقيقي — لا يمكن
التحقق منهما بـ curl.

## هـ. "نسيت كلمة السر" (البند 8)

**لا يوجد أي endpoint.** المصادحة في `apps/api/src/modules/platform/auth/auth.controller.ts`
تملك: `login`, `refresh`, `logout`, `change-password`؛ و`mfa.controller.ts` تملك
`enroll`, `enable`, `disable`. لا شيء لاستعادة كلمة السر. إضافته يتطلّب endpoint جديدًا
في الـ API + قالب بريد + جدول رموز — وهو عمل خادم كامل.

## و. شاشة الترخيص وطلب المساعدة (البند 9)

**شاشة الترخيص:** `GET /billing/activation-requests` → **500**، والسجل يكشف السبب:

```
Error: Platform administrator access required
    at BillingService.listActivationRequests (apps/api/.../billing.service.ts:47:15)
{"level":50,"context":"AllExceptionsFilter","code":"INTERNAL","msg":"Unhandled exception"}
{"statusCode":500}
```

`throw new Error(...)` عاديٌّ لا `DomainError`، فيتحوّل إلى 500 بدل 403. والمستخدم هنا
مستأجر عادي، فالنداء **يفشل دائمًا**. وكذلك `GET /billing/subscription` → `data: null`
فلا اشتراك يعرضه. النتيجة: شاشة ترخيص بلا بيانات.

**طلب المساعدة:** `apps/staff/app/support/help/page.tsx` (56 سطرًا) لا تنادي أي
endpoint على الإطلاق — لا بحث في `grep` عن مسار واحد. هي صفحة ثابتة.

## ز. شاشتان مكتبيتان في نظام سحابي (البند 10)

`apps/staff/app/support/about/page.tsx` يعرض:

- **«عن البرنامج»**: رقم إصدار `0.1.0`، البنية، عنوان الـ API، وثائق الـ API.
- **«تحديث البرنامج»**: نصٌّ يقول «النظام سحابي: التحديثات تُنشر على الخادم… أعد تحميل
  الصفحة».

المالك محق: **وجود هاتين الشاشتين غلطة**. عميل سحابي لا يُحدَّث ولا يُثبَّت ولا يُسأل
عن نسخة. شاشة "تحديث البرنامج" التي تقول "أعد تحميل الصفحة" تَهريجٌ في سياق SaaS.

## ح. البريد الإلكتروني و resend (البند 11)

`GET /api/v1/email/settings` → 200 ويُعيد `"provider":"console"`. الشاشة
(`apps/staff/app/settings/email/page.tsx`, 482 سطرًا) موجودة وغنية، لكن لا شيء فيها
عن **إعادة الإرسال** (resend) كمزوّد. هذا يحتاج:
1. إضافة `resend` إلى سجل المزوّدين في الـ API (`apps/api/src/modules/email/`).
2. إضافته إلى واجهة الإعدادات في staff و platform-admin.

**يحتاج قرارًا** — انظر `05-DECISIONS.md` بند "resend".

## ط. المساعد AI (البند 12)

`GET /api/v1/ai/settings` → 200 ويُعيد `{"enabled":true,"provider":null,...}`، و
`PUT /api/v1/ai/settings` **موجود ومُسجَّل** في مسارات الـ API. فالشاشة تدعم الحفظ؛
ما لا تدعمه هو **مفتاح API الخاص بالمزوّد** (`provider: null`) — أي أن المساعد مُفعَّل
بلا مزوّد. يحتاج:
1. حقل مفتاح مزوّد في نموذج الإعدادات (مشفَّرًا، `secret-box.ts` موجود).
2. ربطه بحالة `provider`.

## ي. شاشات لا يجوز أن تكون في نظام سحابي (البند 13)

قائمة مقترحة، كلها مفاهيم مكتبية من `Desktop_ERP`:

| الشاشة | لماذا لا يجوز |
|---|---|
| `support/about` — «عن البرنامج» | لا يُسأل عميل سحابي عن نسخة |
| `support/about` — «تحديث البرنامج» | لا تحديث يدوي في SaaS |
| `settings/backup` + `settings/restore` | النسخ الاحتياطي مسؤولية المنصة، لا المستأجر |
| `settings/data-rotation` | دوران البيانات سياسة خادم لا شاشة مستأجر |
| `settings/invoice-maintenance` | صيانة الفواتير يجب أن تكون إجراء خادم موثّق |
| `support/report-designer` | يحتاج تقييمًا: مبني على واجهة موجودة أم لا |

**قرار المالك مطلوب قبل أي حذف** — وحذف شاشة يحتاج CR (انظر `05-DECISIONS.md`).

## ك. الجاهزية للإنتاج (البند 14)

**مستوفاة جزئيًّا، وهذه أخبار جيدة:**

- لا `USE_MOCKS` في `apps/staff` ولا `apps/platform-admin`.
- لا بيانات تجريبية مكتوبة (`demo@`, `test@example`, `بيانات تجريبية`).
- لا `NODE_ENV === 'development'` إلا في صفحتي `/design`، وهما محجوبتان في الإنتاج
  بـ `notFound()`.

**ما لا زال يعيق النشر:**
- `.env` يحتوي كلمات مرور بذرة مولَّدة (سليم للتطوير، ويجب ألا يُرفع).
- الأخطاء 500 غير المعالجة (البند و) تُظهر للعميل "An unexpected error occurred".
- شاشة الترخيص والعديد من الشاشات المعتمدة على رايات مطفأة تُظهر 404 للعميل.

## ل. الوكلاء المتوازون (البند 15)

**غير قابل للتنفيذ في هذه الجلسة.** أنا وكيل واحد؛ لا توجد لديّ أداة لتوليد عمليات
فرعية تعمل على نفس المستودع. والأخطر أن التوازي على نفس الشجرة يخلق تعارضات في
`git` و`node_modules` و`pnpm-lock.yaml`.

**البديل العملي:** الجلسات المنفصلة المتوازية على مسارات عمل **لا تتقاطع في الملفات**:
جلسة للتصميم (`packages/ui` + `globals.css` + قشرة staff)، وجلسة للـ API
(`apps/api` + `packages/database`)، وجلسة لشاشات staff. التفاصيل في `05-DECISIONS.md`.
